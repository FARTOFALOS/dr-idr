# Семантическая трассировка DR Lab — исполняемый контур

Машинная форма [DR-LAB-SEMANTIC-ARCHITECTURE 0.1](../meaning/lens/2026-10-13-semantic-architecture/01-DR-LAB-SEMANTIC-ARCHITECTURE-0.1.md)
с поправками [дополнения 0.2](../meaning/lens/2026-10-13-semantic-architecture/02-DR-LAB-SEMANTIC-ARCHITECTURE-0.2-dopolnenie.md).
Она позволяет взять любое утверждение экрана 24 и программно получить его происхождение:
**наблюдение → состояние → вопрос → набор → исходы → расчёт → оценка и опора → допуск → представление (→ выпуск)**.
Можно и в обратную сторону: найти всё, что зависит от изменённого определения, правила или функции.

Это **не** новая онтология и не второй DR Lab. Модуль ничего не вычисляет сам:
- каждое число — то, что опубликовал шлюз SC-1.1 (`lab/contract.py`), уже пересчитанное его эталонными определениями;
- трассировка добавляет проверки, которых шлюз не делает, и отчёт о связях.

Порядок нормативности прежний: решения оператора → `DR-LAB-SC-1.1` → эта трассировка. Расхождение с SC-1.1 — дефект
трассировки.

## Как запустить

```bash
python -B lab/semtrace.py check                         # статические проверки связей (база не нужна)
python -B lab/semtrace.py scene SCENE:ARRIVE-HALF       # трасса одной сцены (нужна база lab/.runtime)
python -B lab/semtrace.py impact CMP:K-POS-1            # что зависит от изменённого определения / функции
python -B lab/semtrace.py why CMP:K-POS-1 PB:B18/EST:K-ARRIVE   # почему: цепочка связей
python -B lab/semtrace.py lineage PB:B18/EST:K-ARRIVE   # от места на экране назад к источникам
python -B lab/semtrace.py q1                            # сохранённые выпуски и исходы Q1 (только чтение)
python -B lab/semtrace.py counterexamples               # шесть видов нарушенных связей: каждый должен быть найден
python -B lab/semtrace.py run --out studies/trace_2026_10_13 --screens   # всё, со снимком экрана и свидетельствами
python -B tests/trace_arch.py [--screens]               # приёмка (ALL GOOD)
.venv-linkml\Scripts\python.exe trace/tools/build.py    # после правки trace/schema или trace/catalog (PYTHONUTF8=1)
```

`--screens` поднимает сервер этой копии на свободном порту (никогда не 8767, 8771, 8772), снимает страницу и
останавливает сервер. Рабочий экран оператора не трогается.

## Что проверяется

Статически (`check`, при сборке и в тесте):
- **REF-RESOLVE, ID-UNIQUE.** Каждая ссылка реестра SC-1.1 и каталога ведёт к существующему объекту своего класса
  (с учётом потомков); идентификаторы уникальны в обоих.
- **CODE-REFS, CHECK-REFS.** Код и проверки по ссылкам существуют: Python — по `ast`, страница — по объявлениям,
  тесты — по функциям и маркерам.
- **ESTIMAND-CHAIN.** У каждой из 59 величин есть вопрос, наборы, исход с эталоном, одна форма утверждения,
  оцениватель, маршрут или пересчёт страницы, привязка SWPC и статус профиля.
- **CLAIM-PROFILE.** Класс формы допустим на каждом наборе; у C1 названо условие; C2 и C3 нет; профиль величины
  совпадает с профилем маршрута.
- **BINDING-COVERAGE.** Каждая величина и форма факта представлены привязкой SWPC §9; у привязки отсутствия есть
  зарегистрированная метка или функция страницы.
- **STANDING.** Решение по профилю берётся из источников. Если статус реестра читается сильнее решения, это должна
  быть зарегистрированная граница.
- **EDITION-ADDITIVE.** Принятый текст SC-1.1 (`bdba7276…`, читается из git) сохраняется построчно в тексте, который
  закрепила линия.
- **CATALOG-COVERAGE.** Все 130 идентификаторов 0.1 есть в каталоге, и в каталоге нет выдуманных.

На сцене (`scene`, `run`, тест):
- **GATE-CONFORMANT.** Ответ прошёл шлюз.
- **BUNDLE-CLAIM.** Величина, форма, класс, набор, маршрут и профиль bundle совпадают с реестром.
- **BUNDLE-COUNTS.** Числитель, знаменатель, опора и неизвестные согласованы между собой и с пересчётом по эталонным
  определениям из записей ответа.
- **IDENTITY.** Семья и снимок выведены заново; повторный расчёт даёт тот же bundle.
- **FUTURE-TARGET.** Свечи сегодняшнего дня после среза заменяются в памяти. Не меняется ни производственный расчёт
  до шлюза, ни ответ после него.
- **FUTURE-MEMBERS.** Будущее аналогов заменяется в памяти: для базовой семьи — после собственной активации, для
  отбора на срезе — после среза. Меняются метки, но не состав. Если ни одна метка не изменилась, проверка не
  засчитывается: она была бы холостой.
- **Q1-ISSUE-MATCH, Q1-STORE.** Сохранённый выпуск того же вопроса отвечает так же и воспроизводится IDENTICAL.
  Идентичности, связи, ревизии и `verify()` хранилищ согласны, байты не меняются.
- **SCREEN.** Элемент страницы привязан к тому же bundle или к проверенному паспорту, показывает значение в его форме
  и зарегистрированные слова.
- **IMPACT.** Обратный обход определений цепочки достигает самого утверждения и его привязки.
- **ACCEPTED-CODE-IDENTITY.** BASE-24 и NOW-1.0 пересчитываются кодом принятого коммита `main` в отдельном процессе и
  дают те же bundle.

## Как читать отчёт

У каждой связи — статус этого прогона:
- **VERIFIED** — проверено сейчас;
- **IMPLEMENTED_UNVERIFIED** — реализовано, но не проверялось;
- **PROPOSED** — предложено, не принято;
- **MISSING** — нет или нарушено;
- **NOT_APPLICABLE** — по смыслу неприменимо.

Обязательная связь со статусом MISSING или блокирующее нарушение делают утверждение **недостоверным**. Отчёт называет
место, а для рабочего экрана прежнее поведение шлюза — снятие числа — сохраняется.

Оценки не сворачиваются в одно «готово», их пять:
1. **Решение по профилю** — из источников: BASE-24 и NOW-1.0 приняты, ARRIVE-24 — вариант для приёмки.
2. **Определённость модели** — все определяющие связи разрешились.
3. **Соответствие реализации** — проверено в этом прогоне.
4. **Машинная проверка показа** — показанное совпало с опубликованным.
5. **Человеческое прочтение** — PENDING, пока H-задачи SWPC не проведены. Его не заменяет никакой зелёный тест.

Три операции записываются отдельно, ни одна не доказывает другую:
- **COMPUTE** — расчёт;
- **PRESENT** — показ на экране;
- **ISSUE** — сохранение выпуска.
