# 22 · Semantic reset созвездий: одна матрица Time × SD, две проекции, frontend-созвездия (27.10.2026)

**Статус:** операторская смысловая рамка следующей реализации базовых R/X-созвездий.  
**Это не новый UI, не изменение SC-1.1 и не новый event engine. Это замена смысловой зависимости под уже принятым визуальным языком экрана.**

## 0. Коротко

Базовый слой должен быть проще накопившейся архитектуры.

Для фиксированной семьи `F` каждая known историческая сессия даёт:

- один `FINAL-R = (time, SD)`;
- один `FINAL-X = (time, SD)`.

Для R и X отдельно строится одна joint-матрица:

`M_e(k,b) = n_e(k,b) / N`

где:

- `e ∈ {R, X}`;
- `k` — общая SD-корзина 0.1 SD на вертикальной шкале торгуемой DR/IDR-сессии;
- `b` — 15-минутная корзина времени;
- `n_e(k,b)` — число сессий семьи, чей итоговый event оказался именно в этой клетке;
- `N` — одна и та же исходная семья.

**Созвездие не является отдельным backend-объектом.** Это frontend-визуализация самых выраженных участков этой матрицы через representative stars, дымку/плотность и существующий язык «дымка и нити».

Правый ряд прямоугольников по цене и нижний ряд прямоугольников по времени являются двумя взаимно связанными проекциями той же матрицы.

## 1. Что поддерживает авторский Time & Price

Публичный материал M7/DRlens/QuantX поддерживает следующую основу:

- maximum retracement — самый глубокий retracement одной сессии после подтверждения;
- maximum retracement time — время этого итогового retracement;
- maximum extension имеет тот же тип пары «время + нормированная цена»;
- автор сначала читает time distribution, затем price/SD distribution;
- одно distribution может иметь несколько выраженных price areas/clusters;
- разные части времени могут иметь разные price distributions.

## 2. Общая геометрия SD

SD не пересчитывается отдельно для каждой 15-минутки.

Для одной торгуемой DR/IDR-сессии существует одна вертикальная нормированная шкала на всём рабочем горизонте:

- `0` — край IDR со стороны подтверждения;
- `−1` — противоположный край IDR;
- `+1` — ещё одна ширина IDR по направлению подтверждения;
- промежуточные значения — те же общие ступени 0.1 SD.

Поэтому клетка

`11:00–11:15 × −0.3 SD`

и клетка

`14:00–14:15 × −0.3 SD`

имеют **одну и ту же вертикальную координату SD** и различаются только временем.

Это важная защита от ложного чтения «у каждого времени своя SD-шкала».

---

## 3. Одна сессия → одна точка R и одна точка X

Для каждой сессии `i ∈ F`:

- `R_i = (t_i^R, u_i^R)`;
- `X_i = (t_i^X, u_i^X)`.

Это итоговые accepted R/X полного горизонта, не PB-L, не SW и не локальный swing.

Один known R голосует ровно в одной `time × SD` клетке R.  
Один known X — ровно в одной клетке X.

Следовательно, базовый слой не имеет проблемы multi-event voting.

---

## 4. Матрица — единственный статистический источник

Для `e ∈ {R, X}`:

`S_e(k,b) = {session i: event e_i landed in SD bin k and 15-minute bin b}`

`n_e(k,b) = |S_e(k,b)|`

`p_e(k,b) = 100 × n_e(k,b) / N`

Это главный estimand базовых созвездий.

Пример при `N = 100`:

| SD \ Time | 10:45–11:00 | 11:00–11:15 | 11:15–11:30 | 14:00–14:15 |
|---|---:|---:|---:|---:|
| −0.2 | 3% | 7% | 4% | 1% |
| −0.3 | 7% | **18%** | 6% | 4% |
| −0.4 | 5% | 12% | 5% | 3% |
| −0.6 | 2% | 11% | 3% | 1% |

`18%` означает:

> у 18% всей семьи итоговый R/X оказался именно в пересечении этого времени и этой SD-корзины.

Это **не** cumulative reach «18% хотя бы дошли до −0.3».

## 5. Два луча UI — две интерактивные проекции той же матрицы

### 5.1 Наведение на SD справа

Если трейдер ведёт мышью по ценовому прямоугольнику, например `−0.3 SD`, нижняя временная полоса раскрывает весь ряд:

- 10:45–11:00 → 7%;
- 11:00–11:15 → 18%;
- 11:15–11:30 → 6%;
- 14:00–14:15 → 4%;
- и т. д.

Самый большой столбец показывает, **когда эта SD-координата была наиболее массовой**, но вторичные времена остаются видимыми.

### 5.2 Наведение на время снизу

Если трейдер ведёт по `11:00–11:15`, правая ценовая колонка раскрывает весь столбец:

- −0.2 → 7%;
- −0.3 → 18%;
- −0.4 → 12%;
- −0.6 → 11%;
- и т. д.

Это показывает, **на каких SD итоговые события концентрировались в эти 15 минут**.

### 5.3 Обычный режим

Без hover экран сохраняет нынешний визуальный язык:

- основные сильные блоки по цене;
- основные сильные блоки по времени;
- наиболее выраженные созвездия;
- связь с фактической ценой и текущим временем.

Новый смысл не требует нового интерфейса. Требуется, чтобы все эти носители происходили из одной `M_e(k,b)`.

---

## 6. Что такое созвездие после reset

Созвездие — **frontend-композиция наиболее выраженной массы joint-матрицы**.

Оно помогает трейдеру за 1–2 секунды увидеть ключевые координаты:

- где по SD;
- когда по времени;
- насколько выражена историческая масса относительно той же F/N.

Созвездие не обязано иметь:

- backend ID «zone R2»;
- connected mask;
- half-height boundary;
- fixed width 0.3 SD;
- membership как отдельный статистический объект.

Визуальный язык текущего 24 — дымка, нити, звёзды, muted amber/sky — сохраняется, если он хорошо читается.

---

## 7. Как не превратить 1000 сессий в шум из 1000 звёзд

Полная статистика считается по **всем** членам `S_e(k,b)`.

Frontend не обязан рисовать одну звезду на каждую сессию.

Разрешённая схема:

1. backend сохраняет полный count и session IDs каждой клетки;
2. frontend выбирает небольшое число **реальных historical witnesses**, а не искусственные точки;
3. полезный уже испытанный вариант 23.5 — один реальный представитель на занятую display-microcell `M5 × 0.1 SD`, выбранный близко к характерному месту;
4. visual mass задаётся полным `n/N`, а не количеством нарисованных stars;
5. остальные сессии не исчезают из процентов, inspector и provenance.

То есть:

> **representative stars = witness layer; дымка/размер/яркость = mass layer.**

Это позволяет N=1000 не превращать в визуальный снег.

## 8. Что именно можно переиспользовать из текущего 24 и 23.5

- real path witness по наведению.

### Из 23.5 сохранить

- общую линейную шкалу массы.

### Не переносить из 23.5

- PB-L вместо FINAL-R;
- обязательное ядро `0.3 SD × 15 min`;
- local-max candidate rule как определение созвездия.

## 9. Что было переусложнено

### 9.1 zone-map-3

`zone-map-3` превращал joint field в отдельные connected regions через:

- 3×3 neighborhood density;
- local peaks;
- half-height mask;
- connected region;
- zone membership.

Это осмысленный clustering question, но он **не нужен как базовое определение Time & Price**.

Проблемой было не наличие алгоритма, а превращение его результата в обязательный смысл созвездия.

### 9.2 PB-0.1

PB меняет сам event: одна сессия может дать несколько локальных H→L→B.

Это отдельный вопрос пути. Он не является «исправленным FINAL-R».

### 9.3 23.5 fixed core

23.5 правильно вернул локальность time×SD, но затем закрепил:

- PB-L;
- `0.3 SD × 15 min`;
- local-max core.

Для нынешнего reset это лишние ограничения.

### 9.4 Universal event engine

Для FINAL-R/X не нужен multi-event voting framework. У нас простой случай:

`one session → one R + one X`.

Универсализацию можно делать только если позднее реально потребуется другой слой.

## 10. Проценты и знаменатель

Для базового `time × SD` поля главный процент:

`n_e(k,b) / N`.

То есть **вся карта находится на одной шкале исходной семьи**.

Не подменять его:

- `n/N_time`;
- cumulative reach;
- number of stars drawn;
- zone-area membership;
- другим conditional denominator.

Дополнительные conditional statistics можно считать в inspector позже, но они не являются базовой массой созвездия.

UNKNOWN не исчезает из N и не становится known membership.

---

## 11. Cumulative reach — другой слой

Если цена с FINAL-R `−0.6`, базовая матрица помещает её в клетку `−0.6`.

Она **не голосует одновременно** в:

- −0.2;
- −0.3;
- −0.4;
- −0.5.

Вопрос «дошли хотя бы до уровня» — отдельная monotone reach ladder и не должен смешиваться с constellation field.

---

## 12. R и X — одна машина

Для R и X используется один pipeline:

`F → final event (time, SD) → 15m × 0.1SD matrix → interactive projections → frontend constellation`.

Разница только в значении event:

- R — итоговый adverse maximum retracement;
- X — итоговый favorable maximum extension.

Не создавать два отдельных cluster engines.

---

## 13. Сегодняшняя цена — отдельный слой факта

Историческая матрица фиксирована для семьи.

Сегодняшний путь может:

- ещё не дойти до сильной клетки;
- уже пройти её;
- находиться рядом;
- быть позже её временной корзины.

Это не меняет historical `n/N`.

Экран может визуально показывать, что время/цена уже прошли область, но не должен ретроспективную FINAL-R/X принадлежность превращать в знание о сегодняшнем будущем.

---

## 14. Cold-start anti-drift contract

Если агент впервые входит в проект, базовый смысл такой:

> **Есть одна фиксированная семья F. Каждая known сессия даёт одну FINAL-R и одну FINAL-X точку в общей системе координат time × SD. Базовая статистика — доля всей семьи в каждой 15-minute × 0.1-SD клетке. Правые price rectangles и нижние time rectangles являются взаимно раскрывающимися проекциями одной матрицы: hover по SD показывает её распределение во времени, hover по времени — её распределение по SD. Созвездие — frontend-визуализация наиболее выраженной массы этой матрицы через representative real witnesses, дымку и нити. Оно не требует zone-map membership, connected boundary или fixed 0.3-SD core.**

Любой исторический модуль можно переиспользовать только если он сохраняет этот event, эту F/N и этот estimand.

---

## 15. Что теперь реально остаётся открытым

После этого reset нет отдельной задачи «найти математическую границу созвездия».

Остаются в основном **presentation/engineering** вопросы:

1. сколько representative witnesses рисовать при больших N;
2. как визуально масштабировать opacity/size, чтобы 4%, 11% и 18% хорошо различались;
3. какой exact idle-state summary текущих rectangles сохранить, чтобы он не противоречил hover cross-sections;
4. как мягко показывать прошедшие/будущие по времени области без изменения historical percentages.

Эти решения не должны менять `M_e(k,b)`.
